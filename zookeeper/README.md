# ДЗ №4. Обеспечение отказоустойчивости средствами Apache ZooKeeper

## 1. Ансамбль ZooKeeper (Docker)

Три сервера ZooKeeper 3.9.5 в Docker (`compose.yaml`): `zoo1`, `zoo2`, `zoo3` с портами 2181/2182/2183.

### Роли серверов

Вывод `stat` для каждого узла до остановки - `logs/zk-status-before-stop.txt`:
- один `Mode: leader`, два `Mode: follower`.

### Потеря одного сервера

Остановлен follower `zoo2` (`docker stop zoo2`) - `logs/zk-status-after-one-stop.txt`:
- оставшиеся `zoo1` и `zoo3` сохраняют кворум 2 из 3, ансамбль работает (1 leader + 1 follower).

### Потеря двух серверов

Остановлены `zoo2` и `zoo1` - `logs/zk-status-after-two-stop.txt`:
- `zoo3` отвечает `This ZooKeeper instance is not currently serving requests` - кворум потерян (1 < 2), ансамбль недоступен.

### Восстановление

`docker start zoo1 zoo2` - `logs/zk-status-recovered.txt`:
- снова 1 leader + 2 follower, кворум восстановлен.

### Эфемерный узел

`logs/zk-ephemeral-test.txt`:
- в сессии создан `/ephemeral_test`, `ls /` показывает узел;
- после `quit` (закрытие сессии) узел автоматически удалён ZooKeeper - во второй сессии `ls /` его уже нет.

## 2. Координатор расчёта (интеграция с ZooKeeper)

Координатор `coordinator.py` использует расчёт из ДЗ №3 (`mapper.py`, `reducer_stats.py`, `cpp_vacancies.csv`). Лидерство - через эфемерный узел `/coordinator/leader`, чекпоинт - в `/coordinator/checkpoint`, результат - в `/coordinator/result`. Таймаут сессии - 10 секунд.

Запуск двух копий:

```bash
python3 coordinator.py --zk 127.0.0.1:2181 --fencing 0 --name A --delay 10
python3 coordinator.py --zk 127.0.0.1:2181 --fencing 0 --name B --delay 10
```

> **Примечание о времени.** В логах координатора (`coordinator-fencing*.log`) время пишется в локальном часовом поясе хоста (UTC+3), а `date +%s.%N` в `leader-change-time*.txt` даёт Unix-время, которое при переводе в UTC даёт время на 3 часа меньше. Например, `STOP at 1793984364.180792` - это `2026-11-06 16:59:24.180 UTC`, что соответствует `2026-11-06 19:59:24.180` в UTC+3. Время смены лидера (≈ 13.3 с) считается как разница между `B became leader` (19:59:37.460, UTC+3) и STOP (19:59:24.180, UTC+3) - часовой пояс на разницу не влияет.

### Этап 3 - без защиты (FENCING=0)

Логи: `logs/coordinator-fencing0.log` (A) и `logs/coordinator-fencing0-second.log` (B).

- A - лидер, обработал чанк 1, сохранил чекпоинт.
- A приостановлен (`kill -STOP`) посреди расчёта.
- B обнаружил исчезновение лидера и стал лидером (`Стал ЛИДЕРОМ после падения предыдущего`), прочитал чекпоинт (`last_chunk = 1`), досчитал чанки 2–5, сделал reduce и **создал** узел результата (`Записал результат (создан узел)`).
- A после `kill -CONT` «проснулся», сессия истекла (`Session has expired`), но A досчитал и **перезаписал** результат (`Записал результат (fencing=0, без проверки версии)`).
- Узел `/coordinator/result`: `"by": "A"`, `dataVersion = 1` (создание B + перезапись A = две записи) - `logs/result-node-fencing0.txt`.
- Результат совпадает с ДЗ №3: `pairs_total = 72027`, `triples_total = 235663`. `diff` с `mapreduce_result.tsv` → `IDENTICAL` (об этом отдельно ниже).
- Время смены лидера: `STOP at 1793979788.905411` (2026-11-06 15:43:08.905 UTC = 18:43:08.905 UTC+3), `B became leader at 1793979820.612111` (2026-11-06 15:43:40.612 UTC = 18:43:40.612 UTC+3) - **≈ 31.7 секунды**.

**Вывод:** без защиты старый лидер затирает результат нового - две записи, `dataVersion = 1`.

#### Сверка результатов с ДЗ №3

Чтобы убедиться, что координатор считает те же пары и тройки, что и `step_mapreduce.py` из ДЗ №3, выполнена сверка:

```bash
diff <(sort mapreduce_result.tsv) <(sort zookeeper/logs/coordinator_result.tsv) && echo "IDENTICAL"
```

**Вывод:** IDENTICAL - файлы полностью совпадают. Это подтверждает, что координатор использует те же mapper.py и reducer_stats.py, тот же CSV и ту же логику shuffle/reduce, что и step_mapreduce.py из ДЗ №3. 

### Этап 4 - с защитой по эпохе (FENCING=1)

Логи: `logs/coordinator-fencing1.log` (A) и `logs/coordinator-fencing1-second.log` (B).

- A на старте прочитал версию узла результата: `Узла результата нет, fencing_version = -1`.
- A приостановлен (`kill -STOP`) после чанка 1.
- B стал лидером, прочитал чекпоинт (`last_chunk = 1`), досчитал чанки 2–5, сделал reduce и **создал** узел результата (`Записал результат (fencing=1, создан узел)`), `dataVersion = 0`, `"by": "B"`.
- A после `kill -CONT` досчитал, попытался записать результат с `fencing_version = -1` → `NodeExistsError` → в логе **`BadVersionError: узел создан другим лидером (fencing=1)`**.
- Узел `/coordinator/result`: `"by": "B"`, `dataVersion = 0` - `logs/result-node-fencing1.txt`. Запись A отклонена.
- Время смены лидера: `STOP at 1793984364.180792` (2026-11-06 16:59:24.180 UTC = 19:59:24.180 UTC+3), `B became leader at 2026-11-06 19:59:37.460` (UTC+3) - **≈ 13.3 секунды**.

**Вывод:** с защитой по эпохе запись старого лидера отклонена, результат остался один (от B).

## 3. Ответы на вопросы

### Почему серверов три, а не два и не четыре?

ZooKeeper принимает решения по кворуму: для $N$ серверов нужно $\lfloor N/2 \rfloor + 1$ голосов.

- $N = 2$: кворум 2. Падение одного сервера оставляет 1 < 2 - ансамбль недоступен. Отказоустойчивости нет.
- $N = 3$: кворум 2. Падение одного оставляет 2 = 2 - ансамбль работает. Это минимальная конфигурация, переживающая отказ одного узла ($f = 1$).
- $N = 4$: кворум 3. Падение одного оставляет 3 - работает; падение двух оставляет 2 < 3 - нет. Четыре сервера переживают отказ только одного, как и три, но требуют больше ресурсов. Выгоды нет.

Оптимум - $N = 2f + 1$, то есть три сервера для $f = 1$.

### Почему защиту по эпохе проверяет получатель записи, а не ZooKeeper?

ZooKeeper - универсальный сервис координации. Он не знает бизнес-семантики приложения: какая эпоха считается актуальной, какой лидер «настоящий», какие записи устарели. Он предоставляет **механизм версий** (`setData` с указанием `version`): если версия не совпала с текущей, операция завершается `BadVersionException`. Это оптимистичная блокировка.

Приложение (координатор) знает, какую версию/эпоху оно прочитало в начале работы лидера. Оно передаёт эту версию в `setData`; если за время расчёта кто-то другой записал результат, версия изменилась - и запись отклоняется. Если бы ZooKeeper сам отклонял «устаревшие» записи, ему пришлось бы знать правила приложения, что противоречит его роли универсального сервиса. Поэтому проверку эпохи выполняет **получатель записи** (координатор), а ZooKeeper лишь гарантирует атомарность сравнения версии и записи.

> Примечание о формате отчета: скриншоты не прикладываются, так как все доказательства (логи запусков, вывод get -s, время смены лидера) представлены в текстовом виде в zookeeper/logs/ и в разделах выше.
